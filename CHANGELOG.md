# Changelog

## Unreleased

- **A supersede now names the panel's whole key set.** The overlay POSTs one fit per visible series while `Supersede` retired every *other* row of the panel, so a two-series panel ended every load with only the last fitted series' row live: the sibling was never retrained and never answered `needTrain` when due, and each load flipped which one it was. Every fit now carries `panelKeys` (the panel's visible series keys, capped at 64: a longer set is refused with `400`, and a panel showing more series than that sends none), the statement clears the stamp on every key in that set and stamps the rest, and a request without the field keeps the previous single-key behaviour. Alongside it: a panel whose metric targets span **two datasources** could only ever store one group's query objects for the scheduler to replay, yet it fitted series from both — the second group's frames are no longer used (its series keep their history and report `The panel trains from more than one datasource; only one can be stored for retraining`)
- **Deleting a model is visible to the process that deleted it.** `drop=model` removed the snapshot from Postgres, but the deleting process's read-through cache kept answering it for up to `snapshotCacheTTL` (30 s), so an admin's removal was invisible to the panel — and to alert evaluation running in that process — until the entry expired. The route now drops that entry.
- **The identity a row stores is capped on the way in, as it already was on the way out.** `querySummary` and the fit's `trainSource` text fields (`seriesName`, `panelTitle`, `dashboardUid`, `querySummary`) are clamped to 200 runes before they are written, so a client cannot park megabytes in a schedule row through the fields the Retrain schedules table renders.
- **The `cacheKey` fingerprint keeps a nested query interval.** `DROP_KEYS` was applied at every depth, so an OpenSearch target's `bucketAggs[].settings.interval` — a field the train rewrite pins as query content — disappeared from the fingerprint and two different histogram resolutions could hash to one stored snapshot. Only a target's own top level drops those fields now, and a bare string `datasource` is read as the uid Grafana means rather than as a type name. A panel whose OpenSearch query differs only in a nested interval gets a new key and refits once.
- **The schema is versioned, and a standalone migrator applies it before Grafana starts.** The DDL moved out of the plugin's `ensureSQL` constant into `pkg/store/migrations/0001_snapshots.sql` and `0002_retrain.sql`, embedded with `go:embed` and applied by the engine in `pkg/store`. `cmd/migrate` (`gpx_forecast_migrate`, `make migrate`) runs that engine out-of-process, so a CI/CD pipeline can prepare a database in front of Grafana: `--dsn` (or the same `FORECAST_STORE_*` / `GF_PLUGIN_*` process env the plugin reads), `--dry-run` to list the pending versions without writing anything, `--timeout` (60s), non-zero exit naming the failing file. Running it stays optional — the plugin applies the same set at its first store use, so an installation that never runs the CLI converges one request late, and a migration failure keeps the per-table fallback (a readable table means the store is ready). A `forecast.schema_migrations` ledger (`id` uuid primary key, `version` unique) records what ran; each file runs in its own transaction opened with `pg_advisory_xact_lock`, so a CI job, every Grafana replica and two replicas serialise instead of racing, and a failing migration leaves behind neither its DDL nor its ledger row. There is no checksum column by design: an applied file is never edited, a new one is added. Needs PostgreSQL 13+ (`gen_random_uuid()`)
- **Every primary key this plugin owns is a uuid.** `forecast.snapshots` and `forecast.retrain` each gained `id uuid PRIMARY KEY DEFAULT gen_random_uuid()` — generated by the database, so no new Go dependency and no writer change — and kept their natural key as `UNIQUE (org_id, cache_key)` / `UNIQUE (scope, org_id, key)`, which is what every read, every `ON CONFLICT` target and the `FOR UPDATE SKIP LOCKED` claim resolves through. A table an older release created is adopted in place: `0002_retrain.sql` still widens the legacy two-column key first, then adds the surrogate key and backfills it, so no row loses its org and no query changes
- **A schedule row now belongs to one org.** `forecast.retrain` is keyed `(scope, org_id, key)` instead of `(scope, key)`, because a panel's `cacheKey` is org-independent — the same dashboard and datasource uids hash the same in every org — so two orgs on one key shared a row: whichever fitted last overwrote the other's `cron`, `enabled` and stored query objects, and the org it overwrote could not even list the row (`GET /schedules` filters by org). `0002_retrain.sql` migrates an existing table in place (the `DO` block only acts while the catalog still reports the two-column key, and every row keeps the org that wrote it), and `ensureSchedules` refuses to serve a table left on the old key rather than share rows between orgs — a runtime user that may not `ALTER` gets `errScheduleKey` on every schedule call, logged and never propagated into a query. `Upsert`'s conflict target is the full key, so org 2's fit writes org 2's row and can no longer touch org 1's
- The scheduler **retrains one org only**: it resolves its own org from `GET /api/org` (once per process, the org its credential belongs to) and claims only that org's rows. Grafana resolves a stored query's `datasourceUid` inside the requesting org, so claiming another org's row would fetch that row's frames as this org's series — or fail forever — and store the result under the other org's key. A row of another org stays due and is refreshed by that org's own overlay load; a refused `/api/org` claims nothing and counts toward the auth auto-disable instead of guessing an org
- Every worker-owned `baseline` row is created by the worker, so `PUT /schedules` now refuses a `baseline` key that does not exist (`404`): a row invented through the API would be claimed by the fleet forever for a hash with no series. Deleting one is allowed for the same reason it was once refused — the worker only re-creates the rows of hashes it still sees, so deleting a retired hash's row is the way out of its `error: no data in the last …` retry loop, and deleting a live hash's row heals on the next tick
- A panel fit reads its own schedule row by key (`Row`) instead of listing the table, which transferred and decoded every worker baseline row — one per `metric_hash` the worker has ever scheduled — to find one row, once per series trained on a dashboard load. The schedule `PUT` echo uses the same lookup
- The provenance merge runs on the read paths only. A request that carries training points writes the whole spec (provenance included) anyway, so `Identify` there was a redundant Postgres round trip on the request the user waits for; the cached-load path it still serves already reads the row (`Due`, `Get`)
- A schedule table created before this release keeps working without a manual step when the runtime user owns the table; otherwise the schedule page reports that it needs `UNIQUE (scope, org_id, key)` applied by the table owner, and the overlay keeps training through `needTrain` as usual
- The **Retrain schedules** table now says what each row belongs to. The overlay records the panel's identity with the fit (`trainSource` gains `panelId`, `panelTitle`, `dashboardUid`) and a one-line label of the training query (`querySummary`, built by the same type-keyed module that rewrites the targets: `PromQL: …`, `PPL: …`, `Lucene: …`, `SQL: …`, `Druid SQL: …`, one line, 120-char cap, empty for TestData). `GET /schedules` derives a `source {dashboardUid, panelId, panelTitle, datasourceUid, seriesName, querySummary, lookback}` from the stored spec — the row's query objects still never leave the backend, a malformed or absent spec costs only that row's Source cell, and the summary is capped at 200 runes outbound — and the table renders it as a Source column whose panel title links to `/d/<dashboardUid>?viewPanel=<panelId>`, with Search matching panel title, series and query as well as the key. None of this enters the `cacheKey` fingerprint, so it cannot orphan a stored snapshot
- The same table now states its two scopes instead of mixing them silently: a Scope cell of `panel` means the row belongs to the current org, and the note above the table explains that `baseline` rows are the worker's fleet-wide rows (`org_id = 0`, listed for every org, and an edit to their cron/timezone/enable state applies to all of them) whose key is the upstream `metric_hash` — their only identity in this store — so the Key cell carries a copy button and the note says how to match a row to a metric
- Identity is captured on every overlay request, not only on a fit: the panel sends `provenance {panelId, panelTitle, dashboardUid, querySummary}` (outside `trainSource`, because a `needTrain` probe never runs the training query) and the backend merges it into that row's spec. A row written before the plugin recorded identity — the cron retrain path has no panel context to fill it in — is therefore identified by the next dashboard load, and an unchanged merge writes nothing. The query summary is built from the panel's own targets rather than the rewritten ones, so the probe and a fit produce the same label instead of a Postgres SQL label that flips with the train window

- The scheduler retrains on **moving** data: `trainSource` carries `relative`/`lookbackMs` when the overlay resolved the window from a lookback, and the backend re-resolves `[now − lookbackMs, now]` at claim time (Debug-logs the resolved window and its kind) instead of refetching the same frozen range every tick. An explicit `trainRange` picker is still replayed verbatim. Neither field is part of the `cacheKey` fingerprint
- A cron retrain now finds the series a labeled panel trained on: the backend mirrors `@grafana/data`'s `getFieldDisplayName` (`config.displayName`, `displayNameFromDS`, frame/field/label parts, the `value 1`/`value 2` duplicate index) and matches `seriesName` against the field name or that display name. When a name matches nothing, a reply with exactly one candidate is accepted instead of failing that row forever; two candidates are still refused
- Only the claim holder can finish a claim: `Finish` (and the worker's `Done`) is `UPDATE … WHERE scope = $1 AND org_id = $2 AND key = $3 AND claimed_by = $owner`, so a retrain that outlived its lease can neither clear a newer owner's claim nor overwrite its `next_run_at`/`last_status` — not even after that owner released the claim itself, which the previous `claimed_by IS NULL OR …` escape hatch allowed
- The scheduler disables itself after three consecutive `401`/`403` refusals from Grafana with one Error log naming `FORECAST_GRAFANA_URL` / `FORECAST_GRAFANA_TOKEN` (or `FORECAST_RETRAIN_ENABLED=false`), instead of retrying a configuration error every tick forever; a tick that got past the fetch resets the count, so a broken datasource never disables it and `needTrain` remains the fallback
- The train-length cap now runs before the training slices are allocated, so an oversized `/api/ds/query` reply is refused with 413-class `errTrainTooLong` instead of allocating first, and the snapshot and schedule probes keep separate readiness/retry state, so a failing `forecast.retrain` DDL no longer turns a snapshot read into an error
- Snapshots can retrain on a cron with no browser open. The app backend (`gpx_forecast`) runs a ticker that claims due rows from `forecast.retrain` (`FOR UPDATE SKIP LOCKED`, so Grafana HA retrains each row exactly once) and re-fits them itself by replaying the stored `trainSource` through Grafana's own `/api/ds/query`. `POST /forecast` now records `trainSource` (datasource uid, the verbatim query objects, the training window, the series name) from a successful fit; it is deliberately **not** part of the `cacheKey` fingerprint, so adding or editing a schedule never invalidates a stored snapshot. The ticker is off with `FORECAST_RETRAIN_ENABLED=false`, and `needTrain` remains the retrain path whenever the scheduler cannot run
- New resource routes `GET|PUT|DELETE /schedules` and `POST /schedules/default` (Admin-only via `backend.PluginContext.User.Role`) plus a **Retrain schedules** app page (a tab beside Overview and Configuration): every row's cron, timezone, next/last run and status, an enable toggle, and delete for either scope. `baseline` rows belong to sibling `timeseries-baselines` and are listed and editable here, but only an existing one: an admin may retime a worker row (`404` for a key the worker never wrote) and may delete one — the worker re-creates a live hash's row on its next tick, so deleting a retired hash's row is what ends its retrain-forever error loop
- `forecast.retrain` (`gpx_forecast` is its only DDL owner) carries `scope` `panel`/`baseline`, `cron`, `timezone`, `enabled`, `spec`, `next_run_at`, `last_run_at`, `last_status` and the `claimed_by`/`claimed_until` lease. The plugin claims only `panel` rows with a spec; the worker claims only `baseline` rows, so neither can claim work it cannot run
- A probe now also returns `needTrain` when the row's `next_run_at` has passed, so a row the scheduler cannot retrain is still refreshed by the next overlay load
- Scheduled retrains reproduce the panel's own model: the stored `spec` carries `alpha` / `beta` / `period` (a cron retrain used to refit with the backend defaults and overwrite the snapshot with them), and a browser fit no longer re-enables a row an admin turned off or moves its cron. A `seriesName` the replayed frames do not carry now records an `error` instead of fitting a different series under that cache key, the DDL fallback checks `forecast.snapshots` and `forecast.retrain` separately before latching ready, and the Configuration page validates the default cron/timezone through `POST /schedules/default` (a rejected default blocks the save) while preserving the jsonData keys it does not render
- Snapshot cache is bounded (256 entries) with a 30 s TTL, so an overlay Retrain reaches the alerting datasource process (and other Grafana replicas) without a restart and resident memory no longer grows with distinct cache keys
- Snapshot store connects lazily and retries (5 s backoff) instead of failing permanently when Postgres is down at plugin start; DDL permission errors are tolerated when the table the call needs already exists
- Inflight limiter bounds Fit / Restore / ForecastRange only; Postgres reads and writes no longer hold compute slots
- `cacheKey` falls back to a pure-JS SHA-256 when `crypto.subtle` is unavailable (plain-HTTP Grafana), producing identical keys
- Aborted overlay loads cancel the in-flight `POST /forecast` and training query instead of only skipping the next request
- Button-only panel editors (Retrain, New alert rule) use their own option paths instead of `trainRange`

- Train and forecast pickers use the dashboard timezone (not a hard-coded browser zone), so calendar days match `resolveTrainWindow` / `resolveForecastWindow`
- **A snapshot survives its schedule row, and nothing keeps a model forever** (v14). `forecast.snapshots` is no longer only written: the retrain ticker collects what nothing refreshes, in one transaction per tick. A snapshot untouched for `FORECAST_SNAPSHOT_TTL` (default `72h`, three daily cycles; `0` disables the sweep; a value below `1h` is refused and the default kept) is deleted; a `forecast.retrain` row idle for the whole window by **both** of its own clocks (`next_run_at` and `last_run_at`, so a failing retrain that keeps writing `last_run_at` is never mistaken for a dead metric) with no snapshot behind it is deleted — which is also how a fleet-wide `baseline` row is collected, since the worker's snapshots live in another schema; and a snapshot with **no** row gets a `panel` row back with the deployment default cron, because a schedule row does not own the model. Retention runs on the same ticker, so `FORECAST_RETRAIN_ENABLED=false` turns it off too, and a sweep failure is a log line, never a failed query
- **A model can be removed explicitly**: `DELETE /schedules?scope=&key=&drop=row|model`. `drop=row` (the default) keeps v12's contract — the row goes, the model stays; `drop=model` deletes the snapshot and the row together, so the tick's reconcile cannot hand the row back, and every row for that key goes with it. A `baseline` key's snapshot is not this process's to delete, so the response says so in a `note` and the worker's own sweep collects it (`SNAPSHOT_TTL`, the same default and rule, in `timeseries-baselines`). The **Retrain schedules** tab gained a *Delete model* action beside *Delete*, and renders that note when it comes back
- **A superseded row is never "due", and a failed row read never rewrites an admin's schedule.** The overlay's probe answered `needTrain` for a retired key: a stale browser tab whose options still hashed it refit that row, and the fit's `Supersede` then un-retired it and stamped the panel's *current* row — after which the live panel's snapshot froze until its next load. `Due` now requires `superseded_at IS NULL`, exactly as the claim predicate does. And a fit that cannot read its own row (a transient store error) now returns instead of falling through to `Upsert` with the deployment defaults, which silently re-enabled a schedule an admin had disabled and reset when it fires; the snapshot is stored either way, so the user's fit is unaffected
- **The schedule routes bound what a row can carry.** A listing projects the stored spec down to the identification keys it can actually show — a panel's query objects no longer cross the wire on every Configuration page load (the scheduler's own read still selects the whole spec) — and every cell-sized string the response carries (the identity fields of the spec, `lastStatus`, which can embed a series name as long as its datasource allows) is capped at 200 runes at both write and read, so a client cannot park megabytes in a table cell
- **The store fails loudly instead of silently.** `forecast.snapshots` now gets the same key-shape probe the schedule table already had, so a table without `UNIQUE (org_id, cache_key)` fails at readiness with an error naming the constraint rather than answering every `Put` with SQLSTATE 42P10; a migration the runtime user was not allowed to apply is logged instead of looking identical to one that ran; and each table's readiness attempt holds its **own** lock, so a probe stuck behind a concurrent migrator's advisory lock no longer queues the other table's reads and writes behind it
- **The app's health probe reports the store it depends on.** `SnapshotStore` gained `Ping` (the memory store is always healthy, the error store reports why the DSN could not be opened), and `CheckHealth` answers with it: a deployment with no DSN stays healthy by design, one whose store is unreachable or unprovisioned is an error instead of an unconditional `ok`
- **A transport failure is not proof that Grafana accepted the credential.** The scheduler's tick classified every non-auth error as "the request got past the wall", so a wrong `FORECAST_GRAFANA_URL` (a dial/DNS/TLS `*url.Error` with no response at all) never counted toward the auth auto-disable and the ticker logged forever. It now counts as neither a refusal nor a success
- **The overlay no longer carries a fallback Grafana already provides.** A panel whose `targets[0]` omits `datasource` trains (Grafana hands the panel's datasource down on every target it sends — observed live), so `trainQuery`'s unused `panelDatasource` parameter was deleted; a target that still arrives bare is reported as `Training query returned no points` instead of being resolved against the org default. Alongside it: a visible series the training frame does not carry now sets a reason instead of drawing history in silence, the Enabled toggle in the schedules table shows the click immediately and reverts when the `PUT` fails, a legacy string datasource ref is a first-class identity in the fingerprint (as it already was in the rewrite, the mixed-frame and alert-rule helpers), `cacheKey` resolves it the same way, the editor's auto-`cacheKey` effect can no longer push a pre-edit query back over a newer edit, the load chain has a rejection handler, and the Retrain button is offered in the empty state too (it used to be unreachable there)
- **The Forecast datasource's fingerprint can match a multi-target panel.** *Copy source from query A* (and the DataSourcePicker path) copied exactly one metric sibling into `sourceTargets`, while the overlay fingerprints **every** visible metric target — so on a Mixed panel with two metric rows the alerting query's `cacheKey` could never equal a stored snapshot and `QueryData` answered its `needTrain` miss forever. Both writers now store the full ordered sibling set, and a live check confirmed the copied key is byte-identical to the panel's stored key and that `QueryData` restores it
- **The overview documents the second shipped executable.** `docs/FUNCTIONAL_OVERVIEW.md` gained the `gpx_forecast_migrate` row with its `--dsn`/`--dry-run`/`--timeout` contract and the ledger/lock facts, the retention and `drop=model` behaviour (F5/F12/F16/F20), the app's landing page (F34), and a dated **pass-5** measurement of the current head with the artifact hashes, the migrator transcripts (a scratch database's `pending` → `applied` → `nothing to apply`) and the live retention/copy/restore observations; its own contradictions were fixed (the datasource editor's key list, the `timeseries-forecast` version, the `superseded_at` column in the scheduler diagram, the two dangling audit pointers, the button-only option keys) and CI now type-checks the plugin-tools `Magefile.go`, which only `gofmt` saw before

## 1.0.0

- App plugin with Go `/forecast` resource
- Nested Forecast overlay panel
- Nested Forecast datasource for Grafana alerting (`QueryData` Restore of overlay snapshots)
- Mixed overlay: ignore Forecast datasource frames for fit and plot; optional Copy source from query A (no auto-fill)
- Overlay options New alert rule: Grafana alerting form with live panel queries (not the Time series Alert tab)
- Load limits: cap train body/length and concurrent Fit / ForecastRange; overlay `maxInflightLoads` (default 1); 413/429 or a panel reason instead of unbounded work
